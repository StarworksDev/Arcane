## 1. What "done" means for the arc

A later Box3D module can register a system and a world resource the same way 2D physics does, without an edit to `Runtime.cpp` and without a Manifold type in a Render or Engine translation unit. The 2D component header is solver-free, the three physics component ids stay in today's order, and `ProjectHost`'s roster check still walks all thirteen types. A new cooked mesh section is written and read by one codec, and the v1 texture and mesh bytes checked in before that move still match. A layout change in a header a game compiles, a change to `ASTRA_ENTITY_BITS`, or a monolithic table whose digest disagrees, fails a check without a person remembering to edit `61`. The bindless table recycles slots after every context that sampled them has retired, and it shares one generated capacity constant with the shader. Mesh bytes and texture bytes are one residency account per device, with a total, two reservations, and a borrowing rule. World pictures, including the first frame a texture or mesh is uploaded, physics step traces, and the checked-in `.arcart` bytes stay identical, on D3D12 and on Vulkan, except for the single ABI-identity bump named in section 7. The arc is complete when those gates are green and fix #11's single process scheduler is in the tree and tested.

## 2. Rules this arc does not get to break

These are already binding. A design that needs an exception is the wrong design.

**Failure is a `Result`, a refusal, or an empty optional.** `Arcane::Result` is Astra's result (`Ecs.hpp:65`). Astra itself is exception-free. Public seams in this arc return that, or the refusal enum the caller already uses (`kInvalidSlot`, artifact `Missing`). They do not throw. A job thread that throws terminates the editor; that class of bug is how the artifact reader was hardened, and the new codec must not reopen it.

**Anything that outlives registry state is keyed by `Identity` GUID.** Frame-local data may carry an `Astra::Entity`, because the id pass consumes it in the same frame. Saved records, residency entries, and bindless lifetimes that survive a reload key by `Guid`. `BodyRecord` already stores one (`Physics2DWorld.hpp:36`). `MeshResidencyEntry` already stores one (`MeshResidencyBudget.hpp:66`).

**Astra's four storages stay separate.** D25's unified `View` reads table, sparse, universal, and relationship storage, and relationships are never encoded as components (`docs/superpowers/specs/2026-10-05-arcane-1.0-roadmap.md`, row D25). This arc does not move the body map into the relationship graph, and it does not add a physics component to stand in for an edge. The solver map stays inside the physics module. When the unified `View` arrives, one translation unit changes.

**Events are a pull model.** Game code reads `StepEvents()` and `FrameEvents()` after the step (`Physics2DWorld.hpp:76-77`). The events spec forbids a listener bus: no registration, nothing stored in module code, nothing running mid-step (`docs/specs/2026-10-08-physics-2d-events-design.md:20`). A 3D solver later gets the same two windows. This arc does not add callbacks.

**The renderer talks to NRI.** D3D12 and Vulkan are the only backends. Descriptor updates, uploads, and barriers go through NRI. This arc does not size a D3D12 heap in one file and a Vulkan set in another, and it does not add a copy-queue path that only one backend can see. Hardware that cannot dynamically index the bindless array is refused, as `MeshNode::Create` already refuses it (`MeshNode.cpp:210-220`).

**Rendering stays multi-view-aware.** F5 fills one world view and leaves `SceneVisibility::views` able to hold more (`docs/superpowers/specs/2026-10-09-f5-unified-world-pipeline-design.md`, section 9). Shadows, extra cameras, and post-1.0 VR are more views of one device. A budget or a bindless table owned by a view will double under a stereo frame. Ownership in this arc is per device. A fence value means something only inside one context's submission timeline (`NriGraphContext.hpp:97-119`). `NriDevice::Graves()` is drain-only (`NriDevice.hpp:165-174`). Reclamation waits on every context that sampled the resource (section 3.5).

**Units stay MKS, +Y up.** Gravity defaults to `{0, -9.81}` (`Physics2DBinding.hpp:23`). The 2026-09-14 research table that still says "+Y down" is stale relative to F4 and to this code. This arc does not reopen it. Box3D's gravity sign is decided in the D5 spec.

**Two physics worlds.** `Runtime` owns both in the sense that the world's registry holds them and the fixed update runs them (`docs/research/2026-09-14-engine-ceiling-deadlock-and-box3d.md:129`). Owning does not mean `Runtime.cpp` constructs either solver. `b3*` types and `Manifold2D::*` types stay behind their façades.

## 3. The six couplings

### 3.1 2D physics is welded into Engine and Render

#### Current state

#### Cost if it stays

F5 Plan 3 edits `CollectPickables` so sprite ids follow the sort key (F5 spec section 6.3). That function currently includes the solver. Plan 3's pick work will either keep Render's Manifold edge or copy it. Plan 2's previews do not step physics, but they link Render, so they link Manifold2D.

D1's id pass, outline, and any physics debug in a perspective view need collider and body shapes in world space. Growing `Access` with a 3D solver puts Box3D types through the same hole. The binding rule is that `b3*` types stay behind the façade (`docs/research/2026-09-14-engine-ceiling-deadlock-and-box3d.md:118`).

D5 cannot register `PhysicsSystem3D` without editing `InstallEngineSystems` and linking both solvers into every host that links Engine. A headless server mints a Manifold world today even when the scene will one day be 3D only. D17 wants 64-bit positions in the physics broadphase (`roadmap` row D17). Those positions have to be written once, in the physics module. A Render translation unit that reads `Manifold2D` `Vec2` has no place to widen.

D25's `ASTRA_ENTITY_BITS 64` recompiles every translation unit that instantiates the system body. That set is Engine, Render's extract, and the server, because each includes `PhysicsSystem.hpp`.

#### Approaches

**A. Module hooks plus a solver-free component header.** `ProcessContext` gains a short list of sim hooks. Registration follows `ModuleAttach`: a function pointer recorded at image load and replayed when the process context exists, because that context may not exist at static init (`ModuleAttach.hpp:5-15`). The pointer is compiled in `ArcanePhysics2D`. It is not a `SystemFactoryEntry` added from a static constructor. `SystemFactoryTable::Add` drops an entry when no owner is open (`SystemFactory.hpp:127-131`), and an engine module attaches before any plugin owner bracket. Game factories stay on that table. The physics hook does not.

The hook is three functions, recorded together.

*Prewarm.* `TypeID<PhysicsWorld2D>::Value()` moves out of `PrewarmEngineResourceTypes`. The physics attach runs it from `AttachAllModules`, which `ProcessContext::Create` already calls after the shared context is installed and before the engine prewarm (`ProcessContext.cpp:30-34`). `EngineResourceTypes.cpp` drops the `PhysicsSystem.hpp` include and the `PhysicsWorld2D` line. The world type stays first-touched inside `ArcanePhysics2D`, which is loaded with the host and is not a hot-reloaded game image. The other resource types stay in the engine prewarm. Their order is not load-bearing (`EngineResourceTypes.hpp:13-15`).

*Component registration.* `RigidBody2D`, `Collider2D`, and `PhysicsBodyRef2D` move to a solver-free header in `ArcaneScene`, at the include path games already use (`<Arcane/Scene/PhysicsComponents.hpp>`). `PhysicsBodyRef2D::handle` becomes the `uint64` `PackBody` already computes (`Physics2DDetail.hpp:105-108`). `BodyHandle` is two `uint32` fields (`PhysicsTypes.hpp:101-104`), so the packed value is the same width. The field stays hidden and not serialized. The header includes no `Physics2DHandles.hpp` and no Manifold header. `RegisterPhysicsComponents2D` remains the function tests call on a bare registry. `Runtime` stops expanding those three types inside `RegisterRoster`.

The hook's register-components function runs in the constructor immediately after `RegisterRoster` of the ten scene types (the list that ends at `WorldBounds`). It registers `RigidBody2D`, then `Collider2D`, then `PhysicsBodyRef2D`. That is the order `EngineComponentRoster` has today, so the thirteen ids stay put. A secondary world that shares the primary registry runs the same function, and the shadow it pushes is the one `Runtime.cpp:305-317` already documents for a second roster handle. `ClearSystems` does not register components again. It only rebuilds schedulers.

*Systems.* `InstallEngineSystems` keeps transform propagation and bounds. In the slot where it currently constructs `PhysicsSystem2D` (`Runtime.cpp:607-611`) it calls each hook's register-system function, so `ClearSystems` brings 2D back without a following `InstantiateModuleSystems`. `PhysicsSystem2D` still declares `Before<TransformPropagationSystem>`. That declaration is the order contract the install comment already relies on (`Runtime.cpp:598-601`). The constructor's frame-begin lambda (`Runtime.cpp:373-376`) becomes a call through the same list. The 2D hook looks the resource up and, when it is present, calls `PhysicsWorld2D::BeginFrame` (`PhysicsEvents2D.cpp:107`). `EnsurePhysics` and `PhysicsEditPass` become calls through the list. `ArcanePhysics2D` registers the only hook this arc adds, and it always registers, so every current host still steps 2D. The scheduler passed to `SetExecutor` is the one `EnsurePhysics` uses today. After fix #11 it is the process scheduler. The hook does not construct a `JobSystem`.

*Dependency direction.* `ArcanePhysics2D` keeps its public edges to `ArcaneScene` and `ArcaneCore`. It gains no edge to `ArcaneEngine`. `ArcaneEngine` and `ArcaneRender` drop `ArcanePhysics2D`. The arrow is physics to Scene, and Engine to Scene. There is no cycle. Staging the DLL is how the hook's image is loaded: the simulating hosts (runtime, editor, server, tests) and the game module descriptor name `ArcanePhysics2D`. A boot with the DLL missing fails the existing `hasPhysics` census rather than stepping an empty world. A private edge is still copied onto consumer include paths (scorecard L13 finding 4, confirmed in the critique), so "make the dependency private" is not this fix.

*ProjectHost roster check.* `EngineComponentRoster`, the list `RegisterRoster` expands, becomes the ten scene types. `PhysicsComponentRoster2D` is the three solver-free types, in today's order. `VerifySharedTypeContext` walks the concatenation, still thirteen types, still from the caller's module, because the header now lives in Scene and `ProjectHost.hpp` can include it without a physics module edge. `NamespaceFacadeTest`'s exact `TypeList` stays that concatenation. The check's "not registered yet" success (`ProjectHost.hpp:87-88`) is why the boot test also asserts the three types are registered and that their ids are the three integers immediately after `WorldBounds`, in roster order. A missing hook must fail that assert.

*What Extract asks the physics module for.* Pick silhouettes stay world-space. When Extract runs collider pass 2 it calls into `ArcanePhysics2D`, which reads the solver and fills the same POD list `CollectPickables` builds today (quads, circles, capsules, boxes, entity id). One list per frame is enough, because a second view sees the same world-space corners.

Debug is per view, and it is not written at step time. Extract fills a solver-free `PhysicsDebugExtractRequest` and the physics module returns a `PhysicsDebugGeometry` (the primitive type `PhysicsDebugGeometry.hpp:78-94` already defines). The request carries:

- the viewport Extract passes to `Begin` today, so a later `Begin` that starts using it is the same call;
- the `Affine2D` of that view, and the request produces no primitives when the view has none (the perspective skip at `ExtractFrame.cpp:447-448`);
- interpolation alpha, taken from `RenderContext2D` when that resource exists, otherwise `0`;
- the optional selected entity, which the module maps through its entity map to the packed `onlyBody` value;
- `physicsWholeWorld` and `playMode`, which keep today's draw gate and set `contacts` from the whole-world flag;
- an optional inspector ask: two packed fixture handles (the pair `DebugCollide` takes), `stepIndex`, and the optional thickness and emphasis `DrawNarrowphaseWorldOverlay` takes.

The module applies that request inside its own translation unit. Ordinary debug calls `GatherPhysicsDebug`. An inspector ask calls `DebugCollide` and then `GatherNarrowphaseWorldOverlay`, and appends those primitives. Render copies the primitive list into the overlay with the same `Line` / `Circle` loop `DrawPhysicsDebug` uses now. No Render header takes a `PhysicsWorld` or a `NarrowphaseTrace`. Two views in one frame are two requests and two results. The snapshots in the Done list are taken from today's gather output before this move, one for ordinary debug and one for the inspector.

`Access` stays for the physics module's own translation units and for tests that are explicitly checking the solver. Its header is no longer reachable from Engine, Render, the editor, or the server.

**Amendment 2026-10-20 (Box3D seam check).** In code the request, silhouette, setter and forwarders carry a `2D` suffix (`PhysicsDebugExtractRequest2D`, `FillPhysicsDebug2D`, ...). A 3D world adds a sibling set. `PhysicsDebugGeometry` keeps its name.

**B. A virtual `IPhysicsQuery` in Core.** Render and Engine call one interface. Manifold2D and, later, Box3D implement it. This removes the friend struct. It also builds the "one solver" façade the 2026-09-14 ruling rejects: 2D queries (fixture silhouettes, planar angle, Z kept from the transform) and 3D queries (hulls, capsules, full quaternions) do not share a useful method set. A fat interface either grows 2D forever or forces the 3D world through 2D types. Virtual dispatch on the pick path is a new ABI surface for a problem the interp buffer already solved with a resource.

**C. Narrow exported functions, Render still links Physics2D.** Replace `Access::Solver` with `BodyPose(entity)` and `ForEachFixture` exported from the physics DLL. Engine still calls `EnsurePhysics` implemented in the physics DLL. This deletes the friend struct and is a smaller edit. Render's module edge remains, `DrawPhysicsDebug` still wants a world object or a new parameter list, and Box3D still cannot join the fixed update without an Engine edit. It misses the target the scorecard set: Render and Engine see physics only through proxies and registered systems.

#### Recommendation

Approach A. The interp buffer is the pattern already in the tree, the factory table is the registration pattern games already use, and B contradicts the two-world ruling. C leaves the edge Plan 3 would extend.

2D stays registered unconditionally, so today's scenes still mint a Manifold world and still step it. The Box3D hook is not added in this arc. The seat for it is the list.

### 3.2 Header-only sim bodies under the pre-attach TypeID rule

#### Current state

`PhysicsSystem2D::operator()` is inline in `PhysicsSystem.hpp:19`. ### 3.4 The plugin ABI is a hand-bumped integer

#### Current state

`kGamePluginABIVersion` is `61` (`AbiVersion.hpp:9-10`). `GamePlugin_ABIVersion` returns the integer the module was compiled with (`GameModule.hpp:372-373`). `Plugin.cpp:59-68` compares that integer with the epoch and refuses, before `Init`, with `PluginResolveError::Kind::AbiMismatch`. That comparison is the load gate.

`Runtime::OpenProject` does not refuse. `Runtime.cpp:822-840` compares `Manifest().engineAbi` with the epoch and logs a warning. The comment records why the check is a warning: it used to be a hard refusal, and the v10 bump locked every host out of every existing project. The stamp says which engine the game DLL was built against. The project's data does not depend on that integer. Loading the stale DLL is the act `Plugin.cpp` refuses. Whether a failed plugin load aborts the process is a stage policy in the same comment: the runtime host keeps `plugin_load` Fatal, the editor keeps it Optional, and the editor self-heals content-only stamps before this check runs.

The remote descriptor stores the epoch (`HostSession.cpp:272`, `desc.abi = kGamePluginABIVersion`). `EngineContext::abiVersion` is documented as that integer (`PluginABI.hpp:1216-1218`). A publisher of the number asks the DLL, because every module bakes its own copy of the header constant (`PluginABI.hpp:1205-1214`). The CRT flavor check is a separate gate, read from the file bytes before `Module::Load` (`Plugin.cpp:104-128`). The digest does not absorb it.

The history in `PluginABI.hpp` is the evidence the integer is not sufficient. v14 records that `Material2DDesc` shrank by deleting `vs`, `ps`, and `paramTextures`, that the struct crossed the plugin boundary by value, and that a module built before the shrink loaded with the gate disarmed (`PluginABI.hpp:144-168`). v15 bumped again for the layout change v14 had named and not covered.

Some layouts are locally checked. `GpuInstance` is `static_assert`ed to 240 bytes because the shader mirrors it (`GpuSceneTypes.hpp:68`). Those asserts cover the structs someone remembered. They do not cover the next one.

The F5 spec still says this branch is ABI 54 (section 8, opening paragraph). The tree is 61. The document and the constant diverge because the constant is edited by hand in a different change from the spec.

Game modules compile a known header set. The spelling guard lists 21 of them (`ArcaneSpellingGuardTest.cpp:34-55`), including `PluginABI.hpp`, `Runtime.hpp`, `Components.hpp`, `PhysicsComponents.hpp`, and `Physics2DWorld.hpp`. A field added to any of those is a layout change the loaded DLL will disagree about, while `GamePlugin_ABIVersion` still returns 61. That list is a spelling scan. It is not the closure of types a game actually instantiates. `Astra::Entity` is `BasicEntity` over `ASTRA_ENTITY_BITS` (`Entity.hpp:149-160`). The default is 32, from a define outside those 21 headers. Stripping preprocessor lines, which the spelling guard does (`ArcaneSpellingGuardTest.cpp:12-16`), drops a `#define` and still would not see a build flag.

The monolithic host does not run the integer check. `PluginHost.cpp:1075-1082` adopts `ArcGameModule_Get()` through `Plugin::FromStatic` and the comment says there is no ABI probe, because `ARC_GAME_MODULE`'s `static_assert` pinned the epoch (`GameModule.hpp:350-352`). The static `PluginVTable` holds the eight function pointers and no digest (`GameModule.hpp:390-396`).

#### Cost if it stays

Plan 2 changes public material types (`MaterialSurface` becoming Surface and Post is already an expected bump in the F5 spec). Plan 3 adds `Camera::primary` and `Camera::sortAxis`, also already expected. Those bumps will be done by hand, and any *other* header edit in the same plans will not. Coupling 3.1's `PhysicsBodyRef2D::handle` change is one of those.

D1 will add by-value fields to rows and material descriptors that cross into game-facing headers. D25 changes `sizeof(Entity)` for every header that stores one. A hand integer that someone forgets to bump is the v14 failure on a 64-bit handle: the module loads, and the stack or the stride is wrong.

#### Approaches

**A. An epoch plus a compiler-derived digest, both checked.** Keep a human epoch in `kGamePluginABIVersion` for logs, `.arcproj`, and the remote descriptor. The digest is a 64-bit hash of a manifest a small tool writes by compiling the game-facing closure with the same defines the game module is compiled with. The manifest is not a hash of stripped header text. A comment edit does not change it. The spelling guard's strip rules stay on the spelling test.

The manifest records three defines by name and value: `ASTRA_ENTITY_BITS`, `ASTRA_ENTITY_VERSION_BITS`, and `ASTRA_MAX_COMPONENTS`. D25's entity-width change is then a digest change even before any struct is revisited. The root types are the by-value structs `PluginABI.hpp` names as crossing the boundary (`EngineContext`, the plugin entry struct, and the component structs in the 21-header list that are not behind an opaque pointer), plus every field type reached from those, transitively. `Astra::Entity` is in that closure. For each type the tool records `sizeof`, `alignof`, and for each field the offset, the field's declared type, and that type's size and alignment. The committed file is `build/abi-digest.txt`. CI fails when a fresh run disagrees. This tool is not the constants generator in section 3.5. It runs after the headers compile, because it asks the compiler. It does not run before project generation.

The module exports `GamePlugin_ABIDigest` beside the epoch. `PluginVTable` gains `uint64_t (*ABIDigest)()`. `ARC_GAME_MODULE` fills that slot in the static table (`GameModule.hpp:390-396`). `Plugin::Load` compares the epoch and the digest at today's integer site (`Plugin.cpp:59-68`), before `Init`.

The static path checks it too. `ARC_GAME_MODULE_ABI_CHECK_` keeps the epoch `static_assert` and adds one: the digest the game translation unit computes under its own defines equals `kGamePluginABIDigest` from the committed manifest. A monolithic game built with `ASTRA_ENTITY_BITS=64` against an engine manifest built at the default 32 fails there, at compile time. `PluginHost`'s static branch (`PluginHost.cpp:1075-1082`) also calls the table's `ABIVersion` and `ABIDigest` before `Init` and refuses with `PluginResolveError::Kind::AbiMismatch` when either disagrees. The `static_assert` covers a module that uses the macro. The call covers a hand-built `PluginVTable`, which is how the mismatched-table test runs without a second engine link. The comment that says the static path has no ABI probe is rewritten to name both checks.

The first landing bumps the epoch once, because the export set and the vtable grow by the digest. Old modules fail closed, which is what the gate is for. `.arcproj` keeps storing the epoch so Hub does not have to grow a field in this arc. The precise check is the plugin load, which sees the image that was actually built. `OpenProject` stays a warning. It does not store the digest, and it does not become a refusal. A project stamped with an older epoch still opens. Its DLL fails at `Plugin::Load` when the epoch or the digest disagrees.

**B. Fold a truncated hash into the existing `uint32`.** No new export. A 24-bit digest collides, and every comment-sized header change looks like an epoch bump in `.arcproj` if the high bits move. The v14 class is caught only until the first collision, and the manifest churn is constant.

**C. CI-only.** A build script fails if the headers change and the integer did not. The load gate stays a single integer. A locally built game DLL copied next to an engine that was built from a different dirty tree still loads. The gate exists because that mix is the failure (`PluginABI.hpp:1208-1214` already explains why a host must not trust its own copy of the constant). CI does not see that pair.

#### Recommendation

Approach A. The epoch stays something a person can say. The digest is what makes a forgotten layout change fail closed, on the user's machine, not only on CI. B spends the only 32 bits we have. C leaves the load path as weak as v14.

Adding a struct to the root list is part of adding a by-value cross-DLL argument. A test fails when a public function in those headers takes or returns a by-value struct that is absent from the list.

#### Done

- A test compiles the manifest and compares it to `build/abi-digest.txt`. Changing a recorded define, a listed type's size or alignment, a field offset, or a field's type without updating the file fails the test. A comment-only edit of a listed header does not.
- `HotReloadPluginBad` still fails the load, and a fixture module built against the previous digest fails the load with the existing ABI error kind, before `Init`.
- A module whose epoch matches and whose digest does not is refused at `Plugin.cpp:59-68`, before `Init`.
- A fixture DLL built with `ASTRA_ENTITY_BITS=64`, epoch equal to the host, digest computed under that define, is refused the same way. The host stays at the default 32 (`Entity.hpp:149-150`). A static `PluginVTable` whose `ABIDigest` returns a different value is refused on the monolithic path (`PluginHost.cpp:1075-1082`) before `Init`.
- Opening a project whose `engineAbi` differs from the epoch still succeeds and still logs the warning at `Runtime.cpp:835-840`.
- A module built from this tree loads, and `GamePlugin_ABIVersion` still equals the epoch in the manifest. The static table's digest pointer equals `kGamePluginABIDigest`.
- No golden moves. Pixels do not depend on the integer.

**Amendment 2026-10-19 (B1 review).** A record that holds a std or Astra container hashes its real `sizeof` / `alignof` / `offsetof` only up to the first container member. The first container and every member after it, and the record's own `sizeof` / `alignof`, hash as 0, because one portable `build/abi-digest.txt` cannot record per-STL container sizes (MSVC Debug and Release differ through `_ITERATOR_DEBUG_LEVEL`, and libstdc++ and libc++ differ again). The Done list reads accordingly: a listed type's size, alignment or offset moves the digest wherever it does not depend on the STL configuration, and a test pins the container boundary with a mutated private member and mutated field orders. The completeness scans enforce field-add detection for the 21 game-facing headers AND the transitive records (every header in the field-type list whose type the manifest roots), and a scan fails any scanned class with private data that neither befriends `Access` nor is allow-listed.

**Amendment 2026-10-20 (B2 review).** The digest is a fold of three group mixes, `FoldGroups(Engine, Input, Client)` (`Core/AbiManifestHash.hpp`), so a game project needs no include directory beyond its own module closure (`build/arcane.lua` is unchanged). The Engine group (`Plugin/AbiManifestEngine.hpp`) holds the three Astra defines and every record an ArcaneEngine-only game can include. The Input group (`Input/AbiManifestInput.hpp`) is `InputSnapshot`. ### 3.5 The bindless table is add-only at 256

#### Current state

`BindlessTable` assigns slots densely from zero and never reuses them. There is no per-slot remove. `Release` buries every descriptor at a caller-chosen fence and empties the table (`BindlessTable.hpp:17-20`, `BindlessTable.cpp:52-74`, `77-94`). Past capacity, `Add` returns `kInvalidSlot` and warns once.

`MeshNode` creates the table at `kBindlessCapacity = 256` (`MeshNode.hpp:588-605`). `mesh.hlsl:155-161` repeats `kMeshBindlessCapacity 256` and says the comment is the whole of the contract, because HLSL cannot include the header. The descriptor range is that fixed size, partially bound, and update-after-set is enabled only when the device cap covers the whole range (`MeshNode.cpp:426-448`). When the cap does not, every `AddMaterial` calls `DeviceWaitIdle` first (`MeshNode.cpp:224-232`, `626-631`). That idle retires every frame in flight. `kMaxFramesInFlight` is 3 (`FramePacing.hpp:39`).

The table is per `MeshNode`, and the node is per `NriGraphContext`. A freed material's slot is gone until the whole table is released, which is teardown. An editor session that streams or reloads distinct materials fills 256 and then drops new ones. The four-cube scene uses four slots (`MeshNode.hpp:595-597`). The ceiling is not visible in today's goldens.

Two contexts on one device have two submission timelines (`NriGraphContext.hpp:90-119`). A fence value from one graph does not retire the other's work, and `NriDevice::Graves()` is drain-only: burying there means destroy at device teardown (`NriDevice.hpp:165-174`). Each context keeps its own graveyard lane.

`ResolveMeshAlbedoSlot` memoizes `Guid` to slot on that context (`NriGraphContext.cpp:681-682`, `740`). The lookup is `Guid` only, and the resolve always asks the texture cache for `ColorSpace::Srgb` (`NriGraphContext.cpp:685-687`). The texture cache's own key is `(Guid, ColorSpace)`, because the same asset in both spaces is two uploads (`NriTextureCache.hpp:101-105`, `323-326`). `InvalidateMeshAlbedoSlot` erases the memo and leaves the slot allocated (`NriGraphContext.hpp:1552-1578`). The cook-completion path calls that erase beside `InvalidateContentTexture` (`EditorAppProject.cpp:828-831`, `EditorAppAssetOps.cpp:211`). `SceneRenderResolver::InvalidateMaterial` clears the CPU mesh-material cache (`SceneRenderResolver.cpp:344-355`) and does not touch a slot. Project switch calls `SceneRenderResolver::Clear` (`EditorAppProject.cpp:2214-2215`) and leaves the GPU table. GPU rows copy `materialSlot`, and a row is rewritten when the resolved slot differs from `lastSlot` (`GpuSceneSync.hpp:243-259`).

#### Cost if it stays

Plan 2 compiles Surface permutations and renders thumbnails and shader-editor previews in their own offscreen graphs (F5 spec section 5.7). Each preview that creates a material and drops it still consumes a slot for the life of that vehicle. Plan 3 stores a bindless texture index on the sprite row (F5 spec section 6.2 and section 8.3). If that index is a second 256-wide table, sprite textures and mesh materials split the ceiling and the shader declares two arrays. D1's material count, plus light cookies and shadow atlases later, will not fit in an add-only 256. A stereo view that owned its own table would double the waste. The per-add idle becomes a hitch on any GPU whose update-after-set limit is below the range, which the code already treats as a supported device.

#### Approaches

**A. A free list inside one generated capacity, reclaimed on the device-wide last-use record.** The capacity integer lives in one source file, `build/engine-constants.lua`, field `bindlessCapacity`, value 256. The script `scripts/generate-engine-constants.ps1` (and `scripts/generate-engine-constants.sh` for the Linux lane) writes two outputs and nothing else:

- `Source/Client/ArcaneRender/src/Arcane/Render/Generated/BindlessCapacity.gen.hpp`, which defines `kBindlessCapacity`;
- `data/shaders/bindless-capacity.hlsli`, which defines `kMeshBindlessCapacity`. `mesh.hlsl` includes that file instead of the literal at `mesh.hlsl:161`. DXC's include path is the shader's own directory, which `compile-shaders.bat` already uses.

This script is not the digest tool in 3.4. The digest is compiler-derived and runs after headers compile. The constants script runs before project generation and before shader compilation. In `scripts/ci/build.ps1` that is a step ahead of `GenerateProjects.bat` (today's first step, `build.ps1:39`). In `scripts/ci/build.sh` it is ahead of the premake generate. `ArcaneRender`'s prebuild then runs `compile-shaders.bat` (`premake5.lua:370`), which sees the hlsl the script just wrote. `data/shaders/generated/` stays the gitignored DXIL and SPIR-V output. The two constant files are checked in, and CI fails if running the script would change them. Raising the capacity later is a one-line edit of the lua field, then the script.

The table still allocates that capacity up front. There is one table per `NriDevice`, shared by every context on that device. `Add` pops a free index or appends. While a material is live its slot does not move, so GPU rows keep a stable index. A scene that only adds still receives 0..n-1 in add order, which is what every current golden's material indices are.

The mapping key is `(Guid, ColorSpace)`, the texture cache's key. A Display view and an Srgb view of one asset are two slots. `m_meshAlbedoSlots` moves off the context and onto the device table.

`Release(Guid, ColorSpace)` is the one free entry. It erases that mapping, and it sets every resolved material and every GPU row whose `materialSlot` equals the released index back to `kInvalidSlot` and marks those rows dirty, so the next `GpuSceneSync` rewrites them (`GpuSceneSync.hpp:243-259`) before the index can mean a new descriptor. It does not destroy the descriptor in the caller. The slot record holds a last-use list: every context that sampled the slot, and the fence value of that context's submit that sampled it. A context that never sampled it is absent. The descriptor, and the texture when this release is also dropping the texture, are destroyed only after every recorded fence has completed. Destruction then runs immediately, because every user has retired, or it is buried in the context that observed the completion, at that context's own fence. It is not buried in `NriDevice::Graves()`, and it is not buried at another context's fence value. The index returns to the free list at that destroy, not when `Release` is called. A shader that sampled the slot on context A's frame N cannot see a new descriptor until A's fence for N has completed, and the same for every other context in the record.

Who calls `Release`:

- **Material destruction.** Slots are shared by albedo, not owned by one material (`NriGraphContext.hpp:1500-1503`). The device table refcounts live materials per `(Guid, ColorSpace)`. `SceneRenderResolver::InvalidateMaterial` and a material-asset delete (`EditorApp::InvalidateAssetCaches` for `AssetKind::Material`) drop those references. The count reaching zero calls `Release`. A material that never resolved a texture does not.
- **Texture invalidation.** The cook-completion and asset-delete sites that today call `InvalidateContentTexture` and `InvalidateMeshAlbedoSlot` call `Release` for both `ColorSpace` values of that `Guid`. `NriTextureCache::Invalidate` already sweeps both spaces (`NriTextureCache.hpp:230-233`), including the chrome context's Display entry (`EditorAppProject.cpp:833-843`). The old "erase the memo and abandon the slot" behaviour goes away. The descriptor and the texture wait on the last-use record together.
- **Project switch.** `EditorApp::ResetPerProjectState` already calls `SceneRenderResolver::Clear` and the contexts stay up. It also `Release`s every mapping on the device table. The incoming project resolves from an empty map. Rows that held old indices are dirtied in that same call.
- **Eviction.** A texture eviction in section 3.6 calls `Release` for that texture's `(Guid, ColorSpace)` before the texture object is destroyed, on the same last-use gate. A mesh eviction frees no bindless slot.

`DeviceWaitIdle` per add goes away on the update-after-set path, and on the other path the idle happens once per frame that actually rewrites a descriptor, not once per slot. Hardware that cannot index the compiled capacity is still refused.

Runtime growth past the compiled array is not part of A. The shader declares a fixed array. An unbounded array, or a second page register, is a different shader and a different NRI range, and `MeshNode.cpp:426-431` records why the range is not `VARIABLE_SIZED_ARRAY`.

**B. Double the descriptor set at runtime.** A new set, a copy of the old descriptors, a rebind, an idle. The shader array does not grow with it unless the shader was compiled unbounded. On a fixed array this is a complicated way to use capacity you could have allocated up front. It also changes slot identity if the copy is not index-preserving, and the GPU row would dirty every mesh.

**C. One 256-slot page per chunk of materials, page index in the high bits of the slot.** Grows without a shader rebuild if the shader indexes `textures[slot]` and the page is a separate bound set selected by a push constant. Plan 3's "one index on the row" becomes two numbers, or a packed uint that every consumer must mask. Two backends have to agree on the packing. The free-list problem remains inside each page.

#### Recommendation

Approach A. The editor's real failure is slots that never return, not a 256 that is too small for the four-cube scene. The generated constant removes the hand-mirrored literal, which is the same disease as the artifact codec, at a smaller scale. B and C change the shader and the row for a ceiling D1 has not measured yet. When D1 measures, it raises the one integer.

There is one table per device, shared by mesh materials and, in Plan 3, sprite textures. Views index it. A preview vehicle on the same device uses the same table, so a thumbnail does not keep a private 256.

#### Done

- A device-less test adds 256 descriptors, releases them, completes every recorded context fence, and adds 256 more. The second wave receives slots. The same test, with any recorded fence still in flight, does not recycle an index.
- A two-context test, device-less, with two mock timelines: context A samples a slot and stays in flight. Context B releases that slot, evicts, and allocates again. B receives a different index. After A's fence completes, the old index may return. A `[gpu]` run of the same shape on D3D12 and on Vulkan keeps `RenderErrorCount()` at 0.
- Four reuse tests, one per caller. Material destruction, texture invalidation, project switch, and texture eviction each: erase the `(Guid, ColorSpace)` mapping, dirty a row that held the index and show the row's slot back at `kInvalidSlot`, refuse to recycle while a second context is in flight, then complete that fence and observe the index return. A later resolve of the same key does not receive the abandoned memo.
- A test that only adds, and never frees, still observes slots 0..n-1.
- `kBindlessCapacity` and `kMeshBindlessCapacity` come from `build/engine-constants.lua`. A test fails if either generated file disagrees with that field, or if the two generated files disagree with each other. The constants script is what `build.ps1` and `build.sh` run before project generation, and shader compilation consumes the hlsl those runs wrote.
- The update-after-set path does not call `DeviceWaitIdle` inside `AddMaterial`. The fallback path calls it at most once per frame. A counter test on a mock device covers both.
- Goldens stay at `diffCount == 0`. No scene in the gate frees a material mid-frame, so indices and pixels stay.

### 3.6 Residency budgets are per vehicle

#### Current state

`MeshResidencyBudget.hpp:28-39` states the mesh budget is per vehicle, not per process. `NriMeshBufferCache::Create` latches `render.mesh.residencyBudgetBytes` (`NriMeshBufferCache.cpp:32`), whose default is 512 MiB (`RenderBudgetSettings.hpp:87`). Every `NriGraphContext` creates its own mesh cache and its own texture cache (`NriGraphContext.cpp:441-445`). The editor's viewport, the thumbnail harvester, and each open document are separate contexts, so each gets a full 512 MiB. The texture cache has no byte budget. The header says that mirrors the texture cache and that a process-wide pool needs an allocator above these caches, not a smaller cvar (`MeshResidencyBudget.hpp:32-39`). It also records the Unreal precedent: a shared streaming pool is the default, and a dedicated mesh pool is a configuration (`MeshResidencyBudget.hpp:41-49`).

Eviction math is already device-free and honest: an entry costs CPU copy plus GPU buffers, a mesh drawn this frame is never evicted, and equal ages tie-break on `Guid` (`MeshResidencyBudget.hpp:84-130`).

First use uploads through NRI's helper on the graphics queue and the helper submits and waits (`NriTextureCache.cpp:568-582`, `NriMeshBufferCache.cpp:213-221`). That drains frames already in flight. The upload ring is a different mechanism: per-frame mapped host buffers for constant data and sprite vertices, fenced by the swapchain pacing fence (`NriUploadRing.hpp:4-13`). It is not a device-local texture uploader. Pointing mesh and texture uploads at it would put device-local resources in host memory, or it would not compile.

#### Cost if it stays

Plan 2 adds more offscreen vehicles (material thumbnails, shader-editor previews) that each latch another 512 MiB and upload on first draw with a queue drain. Plan 3 does not add a vehicle, but the world pass and the overlay share the viewport's cache, so Plan 3 itself is safe. D1 adds shadow and GTAO views. If those views are new contexts, the mesh budget multiplies again. Post-1.0 VR is two views of one world; a per-view budget doubles the resident set of the same meshes. D17's large world is the case the budget exists for, and a budget that is N times 512 MiB does not bound it.

#### Approaches

**A. One account per device, with a total, two reservations, and borrowing.** One account per `NriDevice`. Vehicles charge it. They do not keep a private copy of the budget. Two views in one frame charge a shared mesh once.

**Caps.** `render.mesh.residencyBudgetBytes` stays. Its default is 512 MiB (`RenderBudgetSettings.hpp:87`) and its range is 64 MiB..16 GiB (`67108864`..`17179869184`, `RenderBudgetSettings.hpp:93`). The settings inventory records that default as a budget threshold and cites no measured scene (`docs/superpowers/audits/2026-10-03-settings-inventory.md`, the `kMeshResidencyBudgetBytes` row). Two new fields sit beside it. `render.texture.residencyBudgetBytes` defaults to 512 MiB, so the default total is their sum, 1024 MiB. `render.residency.reservationPercent` defaults to 50. A slice's reservation is `cap * percent / 100` in `uint64` multiply-then-divide, which is 256 MiB at those defaults. `16 GiB * 100` fits in `uint64`, so the range ceiling does not overflow the multiply.

Those two new defaults are provisional. Nothing in the content trees derives them. ReferenceProject's texture source is `Content/textures/uv_marker.png` (179 bytes), its largest mesh source is `Content/meshes/golden_prop.glb` (2124 bytes), and the two cooked artifacts under `ReferenceProject/Intermediate/Artifacts/` are 22172 and 527 bytes. The Aphelyon checkout beside this tree (`D:/dev/starworks/Aphelyon/Content`, read 2026-10-17) holds one `.png` of 28076 bytes and one `.arcmesh` of 265 bytes. Neither tree stores a resident-byte total. The implementation plan's first task measures resident texture bytes and the `MeshResidencyBytes` sum on the golden-gate scenes and on the largest scene that checkout cooks, and it replaces either default in that same change when the measured headroom says so. The predicates below are in terms of the latched caps, so a later default does not rewrite admission.

**Registration.** A tunable is a settings field, and `ARC_CONSTANT` is for an invariant (`Constant.hpp:10-14`). `ARC_SETTINGS` in the owning module's cpp is what enters `CVarRegistry` (`Settings.hpp:16-18`, `RegisterSettings` at `Settings.hpp:144-147`). The cvar name is `"<category>.<field>"`. An empty tooltip is refused (`Settings.hpp:23`).

- `RenderTextureSettings` is declared in `RenderBudgetSettings.hpp` beside `RenderMeshSettings`. Its one field is `std::uint64_t residencyBudgetBytes`, initializer `512ull << 20`. The Settings attribute is `"render.texture"`, `SettingScope::Project`, `ApplyMode::Restart`, `Audience::Game`, with no Dev flag. That matches the mesh budget's audience: the header names the budgets a content author can outgrow (`RenderBudgetSettings.hpp:23-25`), and the texture cap joins that list. The Range attribute is `67108864.0, 17179869184.0`. The tooltip says this is the texture slice of the device account, in bytes, latched at account creation. `ARC_SETTINGS(Arcane::RenderTextureSettings)` is added in `RenderBudgetSettings.cpp` beside the mesh registration (`RenderBudgetSettings.cpp:7`).
- `RenderResidencySettings` is declared in the same header. Its one field is `std::uint32_t reservationPercent`, initializer `50`. The Settings attribute is `"render.residency"`, `SettingScope::Project`, `ApplyMode::Restart`, `Audience::Game`, plus `ARC_REFLECT_TYPE_ATTR(Flags, CVarFlags::Dev)` the way `RenderGpuSceneSettings` marks a pool policy (`RenderBudgetSettings.hpp:74`). The Range attribute is `0.0, 100.0`. The tooltip says each slice keeps this percent of its own cap out of the other slice's borrow. `ARC_SETTINGS(Arcane::RenderResidencySettings)` sits in the same cpp.

`ApplyMode::Restart` is the mode whose consumer reads the value once (`CVarTypes.hpp:134`). The account latches the mesh cap, the texture cap, and the percent when it is created. That is how `NriMeshBufferCache::Create` latches `residencyBudgetBytes` today (`NriMeshBufferCache.cpp:32`), and it is why every budget in this header is Restart: the owner does not resize a live pool (`RenderBudgetSettings.hpp:5-7`). A later publish does not move them.

**Borrowing.** `unusedSurplus(slice)` is `0` when `used >= cap`, `cap - reserve` when `used <= reserve`, and `cap - used` otherwise. A slice's allowance is its own cap plus the other slice's unused surplus. Bytes inside a reservation are not surplus, including when that slice's `used` is under the reservation. A slice may occupy the other's unused surplus. It may not occupy the other's reservation.

**Admission checks the slice allowance and the total.** Charge the new bytes to the requester first. The new entry's `lastDrawnFrame` is `currentFrame`, so it is protected the way `SelectEvictions` protects a mesh drawn this frame (`MeshResidencyBudget.hpp:87-92`). Mesh bytes remain the CPU copy plus the GPU buffers (`MeshResidencyBytes`). Two predicates:

- `overSlice(slice)` is `used(slice) > allowance(slice)`.
- `overTotal` is `used(mesh) + used(tex) > meshCap + texCap`.

Admission stops only when `overSlice(mesh)`, `overSlice(tex)`, and `overTotal` are all false. The requester fitting its own cap is not a stop. `SelectEvictions` already bails on an explicit total (`MeshResidencyBudget.hpp:104-105`); this account does that and the slice check together. The case that separates them: textures occupy 700 MiB and meshes occupy 0, which is a legal borrow (texture allowance `512 + 256 = 768`, sum `700 <= 1024`). Admitting 512 MiB of meshes puts the mesh slice on its cap and drops `unusedSurplus(mesh)` to 0, so the texture allowance falls to 512. Textures at 700 are then `overSlice`, and the sum 1212 is `overTotal`. Stopping because `512 <= 512` would leave 1212 resident against a 1024 total.

Evict whole entries, one at a time, recomputing surplus after each, and stop at the first state where all three predicates are false. That is the same minimum as the budget test that refuses a second eviction once the total is met (`MeshResidencyBudgetTest.cpp:43-53`). An entry with `lastDrawnFrame == currentFrame` is never a victim, on either slice, whichever vehicle asked. Priority:

1. While `overSlice(requester)` is true, the victim is the requester's oldest cold entry, smaller `Guid` on a tie. The reservation does not shield the requester from its own charge. A mesh storm therefore sheds cold meshes before it sheds textures.
2. Otherwise the victim is the oldest cold entry on a slice whose `used` is still above its reservation. Equal `lastDrawnFrame`: a texture before a mesh. Equal frame and the same slice: smaller `Guid`. This arm takes borrowed surplus, and it stops at the reservation: a slice at or under its reservation contributes no victim here. A mesh inside the mesh reservation stays. A texture inside the texture reservation stays.

When the loop ends with a predicate still true, every eligible cold entry is already gone. The frame renders. The once-per-report stays.

The 700 + 512 case, which the test locks, at the provisional defaults. Texture T1 is 188 MiB at `lastDrawnFrame` 1. Texture T2 is 512 MiB at `lastDrawnFrame` 2. Meshes are empty. `currentFrame` is 10. Admit mesh M, 512 MiB, `lastDrawnFrame` 10. Rule 1 does not fire (`512 <= 512`). Rule 2's oldest eligible entry is T1. After T1 leaves, texture `used` is 512 and the sum is 1024, so every predicate is false and T2 stays. Mesh occupancy is 512, texture occupancy is 512, the sum is 1024, and M is resident. The bytes that left are texture bytes.

An evicted GPU object waits on the same device-wide last-use record as a bindless slot (section 3.5). The record lists every context that sampled the entry and the fence value of that context's submit. Destroy runs after every one of those fences has completed. A context that did not sample the entry is not in the list. `NriDevice::Graves()` is not the clock.

**Uploads.** First use stops calling `HelperInterface::UploadData`, which submits and waits (`NriTextureCache.cpp:568-582`, `NriMeshBufferCache.cpp:213-221`). The resident object stays device-local.

- **Staging source.** The destination is the committed device-local object, created as today: `MemoryLocation::DEVICE`, a texture with today's descriptor, a vertex buffer with usage `VERTEX_BUFFER`, an index buffer with usage `INDEX_BUFFER`. The source is host memory. Call the staging payload `alignedBytes`. It is the byte count `RingLayout::Allocate` claims once the cursor is already on the allocation alignment, and it is the size of the dedicated buffer.

  A mesh stays on the ring's 16. The vertex region and the index region are each rounded up to 16, the alignment `GpuScene`'s ring copies use (`kRingAlign`, `GpuScene.cpp:34`), and `alignedBytes` is their sum. The copy is the helper's buffer copy: one `memcpy` of each region's bytes (`HelperInterface.hpp:364`). The ring call is `Allocate(alignedBytes, 16)`.

  A texture takes its footprint from the device. `TextureDataLayoutDesc` requires `offset` to be a multiple of `uploadBufferTextureSliceAlignment`, `rowPitch` a multiple of `uploadBufferTextureRowAlignment`, and `slicePitch` a multiple of `uploadBufferTextureSliceAlignment` (`NRIDescs.h:1712-1715`). Those two values are `DeviceDesc::memoryAlignment.uploadBufferTextureRow` and `uploadBufferTextureSlice` (`NRIDescs.h:1856-1857`), read through `GetDeviceDesc`, which is where the helper reads them (`HelperInterface.hpp:298` and `:306-307`). D3D12 stores `D3D12_TEXTURE_DATA_PITCH_ALIGNMENT` (256) and `D3D12_TEXTURE_DATA_PLACEMENT_ALIGNMENT` (512) unless unrestricted buffer-texture copy pitch is supported, in which case both are 1 (`DeviceD3D12.hpp:516-517`; the constants are `d3d12.h:1462` and `:1464`; the non-Agility path writes the same 256 and 512 at `:584-585`). Vulkan stores `limits.optimalBufferCopyRowPitchAlignment` and `lcm(limits.optimalBufferCopyOffsetAlignment, 16)` (`DeviceVK.hpp:938-941`). The NONE backend stores 1 and 1 (`ImplNONE.cpp:50-51`). The footprint test injects 256 and 512 and does not read the NONE pair. Both fields are powers of two, the alignment `RingLayout::Allocate` requires (`NriUploadRing.hpp:83-85`, asserted at `NriUploadRing.cpp:57-60`). Rounding is the helper's `Align` (`SharedExternal.h:375-376`): `(x + alignment - 1) & ~(alignment - 1)`.

  Source pitches stay the ones the cache writes (`NriTextureCache.cpp:556-565`). BC7 uses `Bc7RowPitch` and `Bc7SlicePitch` (`NriTextureCache.hpp:277-284`). RGBA8 uses `width * 4` and `width * height * 4`. `layerNum` is 1, so each mip is one subresource and `sliceNum` is 1. For that subresource, `sliceRowNum = slicePitch / rowPitch`, `alignedRowPitch = Align(rowPitch, uploadBufferTextureRow)`, `alignedSlicePitch = Align(sliceRowNum * alignedRowPitch, uploadBufferTextureSlice)`, and the mip footprint is `alignedSlicePitch * sliceNum` (`HelperInterface.hpp:305-308`). `alignedBytes` is the sum of those footprints over every mip. That sum is `CopyTextureContent`'s size. `Create`'s `(alignedSize * 4) / 3` when `mipNum > 1` (`HelperInterface.hpp:124-125`) is the helper's upload-buffer guess from mip 0, and the staging size does not use it. The same two alignments are what a 1×1 readback in this tree already applies (`PickOutlineNodes.cpp:271-276`).

  A 1×1 RGBA8 mip has source `rowPitch` 4 and `slicePitch` 4. With row alignment 256 and slice alignment 512, `alignedRowPitch` is 256, `sliceRowNum` is 1, `alignedSlicePitch` is 512, and the footprint is 512.

  The CPU write is the helper's row loop, on the ring and on the dedicated buffer (`HelperInterface.hpp:319-323`). For slice `k` and row `l` in `0 .. sliceRowNum - 1`, copy `rowPitch` bytes from `src + k * slicePitch + l * rowPitch` to `dst + k * alignedSlicePitch + l * alignedRowPitch`. `CmdUploadBufferToTexture` receives a `TextureDataLayoutDesc` whose `offset` is the aligned buffer position, whose `rowPitch` is `alignedRowPitch`, and whose `slicePitch` is `alignedSlicePitch`. Each mip is its own copy. The next mip begins `alignedSlicePitch * sliceNum` bytes later. That step is a multiple of the slice alignment, so a first offset that is a multiple of the slice alignment keeps every later mip offset a multiple of it. The ring call is `Allocate(alignedBytes, uploadBufferTextureSlice)`, and the offset it returns is that first `offset`. The dedicated buffer is `alignedBytes` bytes at offset 0, which satisfies either alignment.

  `alignedBytes` is a multiple of the alignment passed to `Allocate`: 16 for a mesh, `uploadBufferTextureSlice` for a texture. `capacity + 1` is therefore not a value `alignedBytes` can take when `capacity` is a multiple of that alignment. The smallest value strictly above such a `capacity` is `Align(capacity + 1, alignment)`. The slot capacity is the latched `render.uploadRingBytesPerFrame` (default `4ull << 20`, `RenderDeviceSettings.hpp:82`; range 1 MiB..256 MiB at `:113-114`). That range is in bytes with no step, so `capacity` need not be a multiple of the allocate alignment (`4 MiB + 511` is legal). The fit test therefore never uses raw `remaining`: it is `Align(cursor, alignment) + alignedBytes <= capacity`, the same arithmetic `Allocate` performs after aligning the cursor (`NriUploadRing.cpp:62-75`), exposed as one shared helper that both the planner and `Allocate` call. The "fits an empty slot" test below is `alignedBytes <= capacity` (an empty slot's cursor is 0, already aligned). A device-less test pins a non-aligned capacity (`4 MiB + 511`, cursor `4 MiB - 16`, a 512-aligned texture) and asserts the helper and `Allocate` agree that it does not fit.

  - `Align(cursor, alignment) + alignedBytes <= capacity`: take the bytes from the recording context's `NriUploadRing` (`NriUploadRing.hpp:4-13`), the allocate `GpuScene::CopyRows` already uses (`GpuScene.cpp:362-371`). The resident mesh and the resident texture do not live in the ring.
  - `alignedBytes <= capacity` and the aligned fit test fails this frame: `NriUploadRing::Allocate` returns `{nullptr, 0, nullptr}` (`NriUploadRing.hpp:154-161`) and `RingLayout::Allocate` leaves the cursor unchanged (`NriUploadRing.cpp:67-70`). Bury the device-local object on the recording context's lane and retry next frame. `BeginFrame` sets that slot's cursor to 0 (`NriUploadRing.cpp:51-53`, `NriUploadRing.hpp:145-151`), so a payload that fits an empty slot can succeed on the retry.
  - `alignedBytes > capacity`: that null return happens on an empty slot too, so the next frame fails the same way. Do not retry. Create one committed buffer at `MemoryLocation::HOST_UPLOAD` sized to `alignedBytes`, the location the ring's own buffers use (`NriUploadRing.cpp:119`). `BufferUsageBits::NONE` is a legal usage: Vulkan ORs transfer source and destination onto every buffer (`DeviceVK.hpp:21`), and D3D12 places `HOST_UPLOAD` in an upload heap (`DeviceD3D12.hpp:1086`). Map it, write the CPU bytes, and copy from it in this frame. The staging buffer is not a graph resource: it is host-visible, the CPU write finishes before the GPU copy, and the pacing fence retires it, which is the ring's own reason for bypassing graph barriers (`NriUploadRing.hpp:9-13`). The device-local resource is ready this frame. The staging buffer, and not the device-local resource, is buried in the recording context's graveyard at that submit's fence. A resource is not split across frames. A chunk would still have to fit the slot, and the first-use picture is read back on the upload frame, so the payload is staged whole.

- **Command phase.** A Copy node named `upload` is declared at the start of that context's frame, before Batch2D, the id pass, Mesh, and any other node that samples the new resource. One command buffer already records every node, and the executor is the only `CmdBarrier` site (`RenderGraph.hpp:211-218`). The node's exec fn calls `CmdCopyBuffer` for the vertex buffer and for the index buffer, and one `CmdUploadBufferToTexture` per mip with that mip's `TextureDataLayoutDesc` from the staging rules above (`NRI.h`). It does not emit a barrier.

- **Transitions.** The upload node's declared write is `RgUsage::CopyDst` on the texture and on each of the vertex and index buffers. `StateFor` maps `CopyDst` to access `COPY_DESTINATION`, layout `COPY_DESTINATION`, stage `COPY` (`RenderGraph.cpp:109-111`). A buffer then forces layout `UNDEFINED` (`RenderGraph.cpp:125-130`). The copy runs in that state. The write is not the helper's after-state.

  The barrier into the consumer state is the compiler's ordinary edge: it walks declaration order and emits a barrier when the tracked state changes (`RenderGraph.cpp:580-585`). The consumer declares the read, and `StateFor` is the mapping.

  - A sampled texture is `RgUsage::ShaderRead`: access `SHADER_RESOURCE`, layout `SHADER_RESOURCE`, stages `VERTEX_SHADER | FRAGMENT_SHADER | COMPUTE_SHADER` (`RenderGraph.cpp:70-71` and `:99-101`). The helper named only `FRAGMENT_SHADER` (`NriTextureCache.cpp:579-580`). This path uses the graph's `ShaderRead` row. That mask already includes the fragment stage that samples the texture.
  - A vertex-buffer read has no `RgUsage` today. Add `RgUsage::VertexBuffer`. `StateFor` returns access `VERTEX_BUFFER`, layout `UNDEFINED`, stage `VERTEX_SHADER`. That is the stage NRI lists as compatible (`NRIDescs.h:490`) and the helper's after-state (`NriMeshBufferCache.cpp:216`).
  - An index-buffer read has no `RgUsage` today. Add `RgUsage::IndexBuffer`. `StateFor` returns access `INDEX_BUFFER`, layout `UNDEFINED`, stage `INDEX_INPUT` (`NRIDescs.h:489`, helper at `NriMeshBufferCache.cpp:219`).

  A missing `StateFor` case trips the assert that a usage derived `kUnknownState` (`RenderGraph.cpp:150-151`). The mapping-table test walks every enumerator (`RenderGraph.cpp:146-149`), so both new rows are in it. `TextureUsageFor` returns no texture bit for the two buffer usages, as it already does for `IndirectArgs` (`RenderGraphExec.cpp:220-225`). Copy usages already add no texture-usage bit (`RenderGraphExec.cpp:205-210`).

  On the upload frame the upload node imports the resources. A new texture's `ImportTexture` entry is `kUnknownState` (`RenderGraph.cpp:78-79`), so the first barrier enters `CopyDst`, and its exit is the `ShaderRead` triple. The imported-texture exit barrier restores that exit (`RenderGraph.hpp:478-482`). `ImportBuffer` takes no entry and no exit (`RenderGraph.cpp:594-596`): the first barrier leaves `kUnknownState` for `CopyDst`, the consumer read leaves the vertex and index states, and nothing restores the buffers afterwards. Every node that samples the new texture or binds the new buffers in that frame declares the matching read. The binders today are `MeshNode` (`MeshNode.cpp:1143-1145`) and the id pass (`PickOutlineNodes.cpp:611-612`). The first of those reads is where the copy-to-read barrier is recorded. A later read of the same usage is the same state and adds no barrier. Later frames do not import the resource. The texture stays at the `ShaderRead` exit, and the buffers stay in the vertex and index states `CmdSetVertexBuffers` and `CmdSetIndexBuffer` already assume.

- **Failure cleanup.** `CreateCommittedBuffer` or `CreateCommittedTexture` failing leaves the entry not ready and memoized refused, which is today's abandon path. A dedicated staging create or map failing is the same memoized refusal: the same size would fail again next frame. A ring miss for a payload that fits an empty slot (`GpuScene.cpp:364-366` already treats a null ring allocation as a drop) buries the device-local object in the recording context's own graveyard at that context's current submit value, or at fence 0 when this frame never submitted (`NriGraphContext.hpp:131-134`), and retries next frame. The entry is not marked ready. An `Execute` that fails before submit uses the same fence-0 burial. Nothing samples the object.
- **Fence owner.** Ring staging belongs to the recording context's upload ring, retired by that context's pacing fence: the swapchain fence, or the offscreen timeline fence (`NriGraphContext.hpp:81-86`). A dedicated staging buffer is buried at that same fence value on the same lane. The copy and the draw share one command buffer, with the graph barrier between them, so the uploading context samples the result in that same submit. Another context samples it after the uploading context's pacing fence has completed that submit. The wait is a queue wait on that one fence value, recorded in the device-wide last-use record. It is not `DeviceWaitIdle`.

Both backends use this path. There is no new copy queue. The upload ring stays the per-frame host buffer for constants, sprite vertices, and any staging payload that fits the slot. A payload larger than the slot uses the dedicated `HOST_UPLOAD` buffer above.

**B. Two process-wide budgets, no shared account.** Mesh cvar and a new texture cvar, each global, no borrowing. Simpler, and it matches "dedicated mesh pool" as a permanent shape. A texture storm cannot evict meshes, and a mesh storm cannot evict textures, even when the other slice is almost empty. That is two models with a shared word "budget," which is the thing the scorecard asked to collapse. It also leaves the upload hitch, so it only fixes the multiplier.

**C. A single undifferentiated byte pool.** One number, meshes and textures interleave in one LRU. Closest to Unreal's default shared pool. A large thumbnail atlas can evict the visible set, or a unique mesh can evict the UI font atlas, because the age rule does not know which misses hurt. The header's UE note says a dedicated mesh slice is a supported configuration, and our mesh bytes are CPU+GPU pairs while texture bytes are not the same shape (`MeshResidencyBytes` counts the CPU copy on purpose). One undifferentiated counter would either under-count meshes or over-count textures.

#### Recommendation

Approach A. One account, a total that admission enforces together with the two slice allowances, two reservations, borrowing of unused surplus only, and an upload recorded on the context's command buffer in `CopyDst` and then transitioned by the consumer's read. B is the hard split, and it is the choice this arc is not making: the scorecard asked for one account, and B also leaves the upload hitch. C throws away the CPU-plus-GPU mesh count the current accounting was written to keep.

**The proxy math drifts from the solver math.** Collider picking scales fixtures with `appliedScale` and reads the live body pose (`ExtractFrame.cpp:203-218`). **`PhysicsBodyRef2D` layout.** The handle is not serialized, and games are not supposed to spell `Detail::`. Replacing it with `uint64` can still change `sizeof` if `BodyHandle` is not already 8 bytes with the same alignment. 3.4's digest is what fails the build until the manifest is updated. Scene files do not change. Hot reload of a game built before the change fails the digest on purpose.

**Staging the DLL, and the roster that still names the types.** Engine's public edge is why a default game gets physics without listing it (`modules.lua:571`). **Digest noise.** The digest hashes the compiler manifest: the three Astra defines, each recorded type's size and alignment, and each field's offset and declared type. **Free-list use-after-free across contexts.** Recycling a slot one context is still sampling, because another context's fence already retired, is a flicker a settled golden will not catch. The four caller tests (material destruction, texture invalidation, project switch, eviction) each show the mapping gone and the referencing row dirtied before the index returns.

The first-use readback is what proves the picture, on both backends, for a payload that fits the ring and for one that does not. If a later measurement shows a copy queue is needed, it is an NRI feature used from both backends. A ring miss on a payload that fits an empty slot buries the device object and leaves the entry not ready. A payload larger than the slot is staged from a dedicated `HOST_UPLOAD` buffer in that same frame. A partial upload is not sampled.

**Shared residency evicts a preview the author is looking at.** That is the account working. The protection for "drawn this frame" covers the visible preview. A preview that was not drawn is evictable. The once-per-report log is what makes a too-small slice obvious.

**3.1 changes a bit in the physics step.** The largest risk in the arc. The hook must call the same `PhysicsSystem2D` with the same `fixedDt` and the same `stepWorld` flag, and `EnsurePhysics` must still mint before `Advance`. **A clear drops 2D, or a frame-begin callback dangles.** If the hook is stored as a game factory, `ClearSystems` (`Runtime.cpp:577-582`) removes it and a plugin unload (`PluginHost.cpp:531-535`) leaves the world with no physics system until some later caller remembers `InstantiateModuleSystems`.
